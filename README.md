# Kuchbrtna — Soup Kernel Challenge

## Реализация и источники идей

Пакет подключается через solution.apply() до создания модели и trainer. Состав батчей,
LoRA, оптимизатор и расписание не меняются.

| Компонент | Файл / кернел | Что реализовано |
|---|---|---|
| Head и CE в int8 | head8.py / int8_rows_dequant_kernel, head_partial_kernel | Tied embedding/lm_head (151936 × 1536) хранится как int8 по строкам + fp32-масштаб (**приближение**: вес сдвигается не больше чем на полшага квантования), и таблица живёт в **pinned-памяти хоста** (233 МБ не на GPU). Голова идёт кусками словаря по 16 384 строки, кусок приезжает на GPU во втором потоке, пока считается предыдущий. **Один проход**: на каждый кусок logits → частичные статистики строки (max, Σexp, Σexp·x, argmax, logit метки) одним Triton-кернелом; для строк с меткой кусок тут же превращается в exp(x − текущий max) и его произведение с весами копится в fp32 с пересчётом масштаба при росте max (online softmax, как в FlashAttention). Полные logits и полная fp16-копия веса не создаются; эмбеддинг выбирает строки на CPU |
| Head и CE (fp16, запасной путь) | fused_ce.py / lm_head_ce_kernel | Logits частями по 256 строк; online log-sum-exp, loss, entropy, argmax и градиент logits в одном кернеле. Используется, если вес нельзя держать в int8 |
| Интеграция | head_patch.py | Метрики TRL и token loss для rewind; tied embedding не проходит через fp32-апкаст peft (`prepare_model_for_kbit_training`: его fp32-копия рядом с fp16 давала пик при загрузке) |
| RMSNorm | rmsnorm.py / rms_norm_fwd_kernel, rms_norm_bwd_kernel | Слитые forward/backward по строкам, сохранение входа и inverse RMS |
| RoPE | rope.py / rope_rotate_kernel | Split-half rotation q/k и транспонированное преобразование градиента, чтение strided входов без предварительной contiguous-копии |
| NF4 | nf4.py / nf4_dequant_kernel | Double-quantized scale и распаковка NF4 в один запуск, отдельный matmul PyTorch/cuBLAS; поддержан замороженный bias |
| Add + RMSNorm | add_rmsnorm.py / add_rmsnorm_fwd_kernel, add_rmsnorm_bwd_kernel | Residual add и post-attention RMSNorm одним запуском в каждую сторону; сохраняются только s и inverse RMS |
| MLP fp16 | mlp.py | Gate/up и SwiGLU на fp16-пути, сокращение сохранённых активаций; residual остаётся fp32 |
| Удаление паддинга | unpad.py | ~43 % позиций батча — паддинг. Слои работают только с реальными токенами ([1, n, hidden]); attention считается отдельным causal-вызовом SDPA на каждую строку по её реальной длине (строки идут подряд, q/k/v строки — срез, маска не нужна), RoPE берёт cos/sin по позиции каждого токена. Dropout LoRA (p = 0,05) применяется к упакованным токенам: маски — другие выборки того же распределения, чем в прогоне с паддингом (**приближение**; первый шаг совпадает, LoRA B начинается с нуля) |
| Offload активаций | offload.py, unpad.py | Всё, что decoder-слой сохраняет для backward, копируется во втором CUDA-потоке в pinned-память хоста через `torch.autograd.graph.saved_tensors_hooks` (механизм `save_on_cpu`, но со своей ареной, одной пачкой копий и одним событием на слой, не больше 128 МБ «в полёте»; перед головой CPU не ждёт копий, если их меньше 48 МБ); в backward слой i−1 подгружается, пока считается слой i. Чтобы копий было меньше: нормализации сохраняют вход в fp16 (**приближение** ~1e-3 в градиенте), attention хранит только q и сгруппированные k/v (2 головы вместо 12) и пересчитывается в backward (те же числа). Арена (~2,2 ГБ) — под то, что реально сохраняют самые длинные батчи; если батч длиннее, недостающий pinned-кусок берётся по требованию (закрепление памяти стоит ~0,7 с на ГБ, поэтому лишнего не держим). Копии точные |
| Веса NF4 в памяти хоста | wstream.py, nf4.py / nf4_unit_dequant_kernel | Упакованные 4-битные веса всех 196 проекций (~650 МБ) уходят в pinned-память хоста прямо при загрузке модели (сразу после квантования каждого веса bitsandbytes) и лежат там одним блоком по слоям; на GPU слой приезжает **одной копией** (~23 МБ) на слой вперёд по ходу прохода (в backward — назад) и **распаковывается одним запуском кернела** (все 7 весов слоя: программы читают таблицы масштабов своего веса из склеенных таблиц слоя) — 28 запусков на проход вместо 196. `model.to("cuda")`, который делает accelerate при старте обучения, такие веса не трогает. Таблицы масштабов (~20 МБ) остаются на GPU; байты и числа те же |
| Загрузка без пика | wstream.py, head_patch.py | Пик памяти давала не модель, а загрузка: transformers перед загрузкой «разогревает» аллокатор блоком размером со всю модель (~1,07 ГБ), peft копирует эмбеддинг в fp32 (933 МБ). Разогрев на время загрузки отключён (веса всё равно уходят на хост), эмбеддинг грузится сразу в память хоста и кусками превращается в int8-таблицу; peft его не апкастит; веса checkpoint'а приводятся bf16 → fp16 на GPU, а не на CPU (то же округление). Пик загрузки 1 069 → 133 МБ |
| MLP одним узлом | mlp.py | Профиль показал, что шаг ограничен CPU (запуск тысяч мелких операций) и PCIe, а не счётом GPU. Весь MLP (gate, up, SwiGLU, down) — один autograd-узел в каждую сторону вместо цепочек Linear4bit → matmul_4bit → NF4Linear, отдельного SwiGLU и двух приведений типов. Те же кернелы и те же числа. (Пробовали также слить q/k/v и пересчитывать gate/up в backward — оба варианта на T4 оказались медленнее и откатаны) |
| Подготовка датасета | startup.py | Soup токенизирует строки через `datasets.map`, а `datasets` перед этим хеширует функцию с токенизатором через dill (~2 с); передаём отпечаток, посчитанный по строкам и настройкам: те же строки, 2,9 → 0,75 с |
| Компиляция в фоне | warmup.py | apply() запускает каждый кернел один раз на маленьких тензорах в фоновом потоке, пока Soup загружает модель; компиляция с пустого кэша остаётся внутри замера, но не задерживает первые шаги |
| SwiGLU | swiglu.py | Пример организаторов; не заявляется собственным кернелом |

В актуальном CE градиент hidden вычисляется уже в forward, пока chunk logits находится в памяти.
Градиент сохраняется fp16 с масштабом — степенью двойки; backward умножает его на grad_total / scale
и возвращает в исходный порядок строк. Это заменяет старую схему повторного matmul head в backward.
Матрицы умножаются средствами PyTorch/cuBLAS: собственный Triton-код обрабатывает статистики и градиент logits.

NF4 явно использует округлённое fp32-умножение scale (mul.rn.f32) и enable_fp_fusion=False,
чтобы не объединять умножение и сложение в FMA. Плотный распакованный вес всё ещё создаётся временно.
RoPE также отключает FMA и сохраняет промежуточное округление произведений.

Индивидуальные выигрыши компонентов не измерены отдельными ablation-запусками.

Источники по комментариям реализации:
- RMSNorm: Zhang & Sennrich, https://arxiv.org/abs/1910.07467.
- RoPE: Su et al., RoFormer, https://arxiv.org/abs/2104.09864; split-half layout Qwen2 в transformers 5.16.1.
- NF4 / double quantization: Dettmers et al., QLoRA, https://arxiv.org/abs/2305.14314; формат bitsandbytes, https://github.com/bitsandbytes-foundation/bitsandbytes.
- int8 по строкам с absmax-масштабом: Dettmers et al., LLM.int8(), https://arxiv.org/abs/2208.07339.
- Offload активаций через saved-tensor hooks: `torch.autograd.graph.save_on_cpu`, https://pytorch.org/docs/stable/autograd.html#saved-tensors-hooks;
  offload весов по слоям — идея ZeRO-Offload / ZeRO-Infinity (Ren et al., https://arxiv.org/abs/2101.06840), реализация своя.
- Слияние частичных softmax-статистик по кускам словаря: FlashAttention (Dao et al., https://arxiv.org/abs/2205.14135).
- Online softmax: Milakov & Gimelshein, https://arxiv.org/abs/1805.02867.
- Chunked head/loss: Soup stream_loss_chunk (#1693 в комментариях), https://github.com/MakazhanAlpamys/Soup;
  идея fused linear CE из https://github.com/linkedin/Liger-Kernel, без подключения библиотеки.
- SwiGLU: стартовый пример https://github.com/MakazhanAlpamys/soup-kernel-challenge.

Исходники объявляют собственную реализацию указанных кернелов; независимый аудит происхождения кода не выполнялся.

## Как запустить

Импортировать templates/kaggle_notebook.ipynb в Kaggle; GPU T4 x2, Internet On.
Используется одна карта. REPO_URL = https://github.com/LilKiddq/hackathon.git.
Финальный коммит и ссылка на публичный Kaggle-ноутбук — в [SUBMISSION.md](SUBMISSION.md).

```bash
python task/prepare_data.py
python -m pytest solution -q
python harness/run_task.py
python harness/check_rules.py
python harness/score.py runs/result.json
```

Измеренный код решения: v33, коммит `cda3a4f` (последующие коммиты меняют только документацию). Команда: Kuchbrtna.

## Результаты и ограничения

Kaggle Tesla T4, `python harness/run_task.py --repeats 2` (как у жюри: база, решение, решение, база;
среднее двух запусков каждой стороны), открытые строки, seed 1, код решения v33 (`cda3a4f`).

| Метрика | Base Soup | Решение | Отношение |
|---|---:|---:|---:|
| Полное время `soup train`, с | 78,0 (76,89 / 79,09) | 50,7 (50,33 / 51,03) | **1,539×** быстрее |
| Пик GPU-памяти (nvidia-smi), MiB | 14 345 | 735 (735 / 715) | **19,52×** меньше |
| Eval loss на отложенных строках | 2,04965 | 2,04922 | −0,021 % |
| Медианный шаг обучения, с | 0,860 / 0,904 | 0,416 / 0,430 | ~2,1× |
| Обучающий цикл (64 шага), с | 54,2 / 56,9 | 28,5 / 29,2 | ~1,9× |

`check_rules.py`: все 10 проверок PASS; наши кернелы — 13,0 % времени обучения (минимум из двух запусков,
шаги 3+); кривая loss: первый шаг +0,18 %, среднее 0,09 % (допуск 1 % и 3 %). `pytest solution`: 57 passed;
регрессионные тесты Soup: 79 passed. В логе каждого запуска решения: где рос пик аллокатора
(`setup 133 MiB … step 39 forward 432 MiB`), сколько весов ушло на хост при загрузке (196 и эмбеддинг), сколько
pinned-памяти заняли активации (2 100 из 2 257 MiB, без кусков по требованию).

Как менялся результат (каждая строка — свой полный прогон `--repeats 2`; отношение по времени зависит и от
скорости базы в сессии, поэтому для сравнения версий смотрите и абсолютное время решения):

| Версия | Что добавлено | Время решения | Скорость | Память (пик) |
|---|---|---:|---:|---:|

| v8 | удаление паддинга, attention по строкам | 55,7 с | 1,58× (база 87,7 с) | 3,22× (4 453 MiB) |
| v12 | offload пар MLP, датасет без хеширования, trl без второго скана пакетов | 52,5 с | 1,51× | 4,49× (3 197 MiB) |
| v13 | offload всех активаций слоя, веса NF4 на хосте | 58,0 с | 1,36× | 9,05× (1 585 MiB) |
| v14 | голова и эмбеддинг в int8 | 59,5 с | 1,31× | 10,62× (1 351 MiB) |
| v19 | int8-таблица на хосте, голова за один проход | 57,7 с | 1,36× | 11,50× (1 247 MiB) |
| v20 | загрузка без разогрева аллокатора, эмбеддинг сразу на хост | 57,4 с | 1,36× | 12,89× (1 113 MiB) |
| v22 | attention: q и сгруппированные k/v + пересчёт; dropout LoRA на упакованных токенах | 56,2 с | 1,40× | 17,39× (825 MiB) |

Выбор между v28 (629 MiB, 53,3 с) и v33 (735 MiB, 50,7 с) сделан по формуле баллов (35·ln s и 30·ln m):
секунда времени здесь весит больше, чем 100 MiB памяти. Распаковка слоя одним запуском держит на GPU
fp16-веса всего слоя (~94 МБ) — отсюда +100 MiB к пику.

Ограничения:
- **Приближения три, остальное точно**: int8-таблица головы/эмбеддинга (loss первого шага +0,18 %),
  сохранённые для backward входы нормализаций в fp16 (~1e-3 в градиенте), маски dropout LoRA тянутся для
  упакованных токенов (те же p = 0,05 и распределение, другие случайные выборки). Eval loss −0,021 %.
- Основное время шага — матричные умножения cuBLAS (на T4 ~0,13 с на шаг) и копирование через PCIe
  (~0,24 с на шаг хост→GPU в профиле, частично перекрыто счётом). Свои GEMM-кернелы мы не писали.
- Пик памяти (~0,7 ГБ) — CUDA-контекст (~0,2 ГБ), рабочий набор одного слоя на самом длинном батче
  (распакованные веса слоя, активации MLP), копии «в полёте», таблицы масштабов NF4, LoRA с Adam.
- Pinned-память хоста: ~2,2 ГБ арена активаций + ~0,9 ГБ весов и int8-таблицы (у Kaggle 30 ГБ RAM).
- Время на Kaggle плавает между сессиями (база 76–93 с); отношение мерить в одной сессии. Замер на открытых
  строках; на скрытых длины батчей и время немного отличаются (более длинный батч возьмёт pinned-память по
  требованию, на GPU ничего не останется).
- Отдельные ablation-запуски по каждому кернелу не делались; вклад видно по таблице версий.
