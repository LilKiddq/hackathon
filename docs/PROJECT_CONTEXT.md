## 1. Задача

**Soup Kernel Challenge, Decentrathon 6.0.** Дедлайн: **31 октября 2026, 23:59 по Астане (18:59 UTC).**
Команда Kuchbrtna, репозиторий `https://github.com/LilKiddq/hackathon` (создан платформой).

Нужно ускорить и/или облегчить по памяти фиксированный запуск `soup train` (soup-cli 0.77.0) на Kaggle T4
своими Triton-кернелами, подключаемыми через `solution.apply()`. Задача (`task/task.yaml`, менять нельзя):
Qwen2.5-1.5B-Instruct, 4-бит NF4 (double quant), LoRA r=16 alpha=32 dropout 0.05 на q_proj/v_proj,
batch 4, max_length 512, 256 казахских инструкций (alpaca), 64 шага, fp16 (на T4 нет bf16), без
gradient checkpointing, SDPA attention, adamw_torch, cosine. TRL `SFTTrainer` (Soup-подкласс
`RewindSFTTrainer`): loss только по токенам ответа; TRL каждый шаг считает entropy и mean_token_accuracy из
логитов, Soup пишет loss каждой строки в `rewind.jsonl`.

### Баллы (100)
- **20 — допуск, всё или ничего:** все 10 проверок `harness/check_rules.py` + код-ревью жюри.
- **35 — скорость:** `35 * ln(s) / ln(s_best)`, s = время базы / наше время (полное время `soup train`,
  включая загрузку модели и компиляцию Triton). Выигрыш < 5 % = 0.
- **30 — память:** `30 * ln(m) / ln(m_best)`, m = пик базы / наш пик (nvidia-smi, раз в 100 мс, сумма по GPU).
- **15 — README:** что сделано (с источниками идей), как запустить, результаты и ограничения (по 5).
- При равенстве выше команда с лучшей памятью. Жюри: база, решение, решение, база (`--repeats 2`), на скрытых
  строках того же датасета и другом seed.

### 10 проверок `check_rules.py`
1. все запуски завершились; 2. нет готовых кернел-библиотек (unsloth, liger, xformers, flash-attn, torchao…);
3. свои `@triton.jit` из `solution/` запускаются в каждом запуске (кернелы примера `example_*` и их копии не
   считаются); 4. свои кернелы ≥ 5 % времени обучения (CUDA events, шаги 3+, минимум по запускам);
5. те же настройки/выходы Soup (шаги, адаптер, метрики, токены по шагам, rewind; entropy/accuracy/rewind ±3 %);
6. кривая loss: первый шаг ±1 %, среднее ±3 %; 7. eval loss не выше базы больше чем на 0,5 %;
8. время и память не хуже базы больше чем на 10 %; 9. чистый замер (T4, GPU простаивают на старте < 1000 MiB,
   одна GPU, аллокатор harness, пик nvidia-smi ≥ 97 % reserved PyTorch); 10. 79 тестов Soup проходят с `apply()`.

### Жёсткие правила
- Нельзя менять `harness/`, `tests/`, `task/`; нельзя менять модель, данные, батчи и их порядок, шаги, LoRA
  (включая dropout), оптимизатор, расписание, переключатели Soup (gradient_checkpointing, activation_offloading,
  use_liger, packing, padding_free…), выходы Soup.
- Можно: свои Triton-кернелы, autograd-функции, патчи transformers/peft/bitsandbytes/Soup; **пересчёт или
  offloading в своём коде** (время считается); **удаление паддинга внутри батча** (смешивать батчи нельзя);
  идеи чужих кернелов со ссылкой на источник, но не их код.
- Нельзя CUDA graphs (harness не видит кернелы), нельзя «другое поведение под замером/в тестах», готовые кэши.
- Данные (датасет) в репозиторий не класть.

## 3. Как запускать (Kaggle)

1. Ноутбук из `templates/kaggle_notebook.ipynb`; Settings: **GPU T4 x2**, **Internet On** (нужен аккаунт с
   подтверждённым телефоном). В первой ячейке: `REPO_URL = "https://github.com/LilKiddq/hackathon.git"`,
   `COMMIT = ""` (= ветка main) или имя ветки/хеш коммита.
2. Перед запуском проверить, что GPU пусты: `!nvidia-smi --query-gpu=index,memory.used --format=csv` (≈0 MiB).
   Если нет — остановить сессию (кнопка ⏻) и запустить заново.
3. **Run All и не прерывать** до конца. Прерванный `run_task.py` оставляет живой процесс обучения на GPU
   (harness запускает его в отдельной группе процессов) → следующий прогон падает на проверке 9, а база — по OOM.
4. Официальный замер: `!cd /kaggle/working/repo && python harness/run_task.py --repeats 2` (~25 мин).
   Быстрая итерация: `--only solution --out runs_try`; профиль: `--only solution --out runs_try --profile`.
5. Полезная ячейка со временем шагов:
   ```python
   import json
   r = json.load(open("/kaggle/working/repo/runs/result.json"))
   for side in ("base", "solution"):
       for run in r["runs"][side]:
           m = run["metrics"]
           print(side, "wall", run["wall_s"], "| loop", m["train_loop_s"], "| steps 3+", m["timed_loop_s"],
                 "| apply", m["apply_s"], "| median step", m["median_step_s"])
   ```
6. Профиль (топ кернелов GPU):
   ```python
   import json
   p = json.load(open("/kaggle/working/repo/runs_try/solution_profile/profile.json"))
   total = p["total_gpu_us"]
   for k in p["kernels"][:30]:
       print(f'{100*k["time_us"]/total:5.1f}%  {k["time_us"]/1000:8.1f} ms  x{k["count"]:<6} {k["name"][:110]}')
   ```
7. Не запускать команды через `subprocess.run(...)` в ячейках — их вывод в Kaggle не виден; использовать `!...`.

Локально без GPU можно проверять кернелы через интерпретатор Triton (`TRITON_INTERPRET=1`, CPU-тензоры) и
регрессию: `SOUP_APPLY_SOLUTION=1 python -m pytest tests -q` (должно быть 79 passed).

## 4. Устройство решения (`solution/`)

`apply()` (`solution/__init__.py`) ставит патчи в таком порядке: пример SwiGLU → MLP fp16 → RMSNorm → add+RMSNorm
→ unpad (оборачивает уже пропатченный слой) → RoPE → Qwen2ForCausalLM.forward → TRL compute_loss → Soup setup →
bitsandbytes matmul_4bit → фоновая компиляция. Все патчи классовые/модульные и откатываются на оригинал для
неподходящих входов (CPU, другие dtype, eval, генерация, моки в тестах Soup).

| Файл | Что делает | Важные детали |
|---|---|---|
| `fused_ce.py` | `lm_head_ce_kernel`: lm_head + cross-entropy + entropy + argmax без полных логитов [4×512×151936] | Чанки по 512 строк, только строки с attention; online softmax; размеченные строки идут первыми; **градиент по hidden считается в forward** (логиты чанка перезаписываются градиентом, сразу matmul с головой), округление в fp16 на масштабе 2^k ≈ 256·N, backward только домножает на grad_total/2^k. Микробенчмарк: 1,83× быстрее, 5,8 ГБ → 0,6 ГБ |
| `head_patch.py` | Подключение fused CE | `Qwen2ForCausalLM.forward` (при `_kc_active`) отдаёт loss без логитов; `trl.SFTTrainer.compute_loss` логирует entropy, num_tokens, mean_token_accuracy по формулам TRL 0.29.1 и кладёт token_loss в `trainer._soup_chunked_step` (так rewind Soup берёт loss строк без логитов); tied embedding/lm_head хранится в fp16 (в чекпойнте bf16 → точно), выход эмбеддинга hook-ом → fp32; в начале `_setup_transformers` запускает фоновое закрепление памяти для offload |
| `rmsnorm.py` | `rms_norm_fwd/bwd_kernel`, fp32 | Для backward хранит только x и rstd |
| `add_rmsnorm.py` | `add_rmsnorm_fwd/bwd_kernel` (тиммейт 3) | residual add + post-attention RMSNorm в одном запуске; патч `Qwen2DecoderLayer.forward` |
| `rope.py` | `rope_rotate_kernel` (тиммейт 1, доработан) | Целые аргументы не специализируются (`do_not_specialize`), иначе перекомпиляция каждый шаг; под fp16 autocast хранит q/k сразу в fp16 (то же округление, что сделал бы SDPA); бит в бит с transformers |
| `nf4.py` | `nf4_dequant_kernel`: распаковка NF4 с вложенным absmax в один запуск | Бит в бит с bitsandbytes (произведение code2·absmax2 округляется до сложения: `mul.rn.f32`, без FMA); запись 32-битными словами; патч `bitsandbytes.matmul_4bit` для training-пути (fp16 вход с градиентом, замороженный bias); дальше cuBLAS |
| `mlp.py` | Qwen2 MLP на fp16-пути | gate/up/down получают fp16 вход и отдают fp16 (те же значения, без fp32-копий); SwiGLU — кернел примера (не наш) |
| `unpad.py` | Удаление паддинга внутри батча | ~43 % позиций — паддинг. После эмбеддинга слои работают с [1, n_real, hidden]; attention — отдельный causal SDPA на каждую строку по её реальной длине (строки подряд, q/k/v — срезы), RoPE по позиции каждого токена; dropout LoRA тянет маску для формы с паддингом и упаковывает (те же маски и RNG); выход модели распаковывается обратно для головы. Если паддинг не справа — старый путь с раскладкой q/k/v. Совместим с gradient checkpointing |
| `offload.py` | Offload gate/up MLP в pinned-память хоста | Копия на втором CUDA-потоке сразу после SwiGLU, GPU-тензоры освобождаются после окончания копии (не больше 3 слоёв «в полёте»); в backward пара подгружается на слой раньше; арена ~2,06 ГБ pinned закрепляется в фоне во время загрузки модели (размер из config.json в кэше HF); при ошибке закрепления — работа без offload |
| `warmup.py` | Компиляция всех кернелов в фоне во время загрузки модели | Маленькие тензоры с теми же dtype и делимостью на 16, что у настоящих запусков; daemon-поток, ожидание ≤ 120 с; после — `empty_cache` |
| `swiglu.py` | Пример организаторов | Не засчитывается, но работает (используется MLP и offload) |
| `test_kernels.py` | 45 тестов против PyTorch/transformers/bitsandbytes | Запуск: `python -m pytest solution -q` на GPU |

`tools/bench_kernels.py` (тиммейт 1) — микробенчмарки кернелов; результаты в `evidence/bench_kernels.md`.

## 5. Подводные камни, на которые уже наступили

- **`tl.constexpr` для длины/страйдов** → Triton перекомпилирует кернел каждый шаг (длина батча меняется), а
  компиляция входит в замер. Варьирующиеся целые — обычные аргументы, плюс `do_not_specialize` (Triton
  специализирует целые по делимости на 16).
- **FMA**: `a*b + c` Triton сливает в одну инструкцию → отличие в последнем бите от PyTorch/bitsandbytes.
  Для точности — `enable_fp_fusion=False` или `mul.rn.f32` через inline asm.
- **Доля кернелов (проверка 4)**: быстрые memory-bound кернелы занимают мало времени; первые версии давали 2 %.
  NF4-кернел (работает во всех 196 слоях) поднял долю выше 5 %.
- **Отдельный CUDA-поток** получает свой workspace cuBLAS (+44 MiB) — фоновую компиляцию делать на default stream.
- **Зависший процесс на GPU** (после прерванной ячейки) → «GPUs not idle at start», база падает по OOM.
- **Шум Kaggle**: база 76–88 с между сессиями; сравнивать только отношение внутри одной сессии.
- **Патчи от Codex**: CRLF в файлах ломал декораторы; архивы на старом `main` затирали чужие изменения —
  присылать `git format-patch` на актуальном `main`.
- Unpad ускорил меньше ожидаемого (+~10 % шага вместо 43 %): на T4 матрицы такого размера считаются «волнами».

## 6. Идеи, которые не сделаны (с оценкой)

- Offload входов нормализаций (наши autograd-функции, fp32 x): ≈ −0,5 ГБ, но +2–3 % времени (PCIe и так почти
  загружен на больших батчах). Примерно ±2 балла.
- Offload активаций LoRA и attention через `torch.autograd.graph.saved_tensors_hooks`: до −0,8 ГБ, рискованнее.
- Держать tied embedding/lm_head на CPU и подгружать по частям: −0,47 ГБ, но +~8 % времени.
- Пересчёт (recompute) MLP: −1,5 ГБ, но −10 % скорости — по формуле баллов невыгодно.
- Ускорить NF4 (сейчас ~210 ГБ/с из ~300), слить LoRA (dropout + A + B), уменьшить число запусков (CPU-накладные
  ~15 % шага).

## 8. Как работает команда

Капитан (владелец репозитория) — единая точка: тиммейты присылают ему `.patch`, он передаёт их на ревью, после
проверки они вливаются в `main`. Любое изменение кода сначала в отдельной ветке, потом прогон на Kaggle
(`--repeats 2`, все 10 проверок), и только потом `main`. Код решения сейчас считается замороженным: дальнейшие
эксперименты — только в отдельных ветках.
